# LLM 任务路由问题报告与后续优化方案

更新时间：2026-05-04

## 1. 当前背景

当前 `robocrew_client_agent` 已经实现了文字/语音混合控制入口，并接入了：

- RoboCrew 官方 XLeRobot 导航/头部工具。
- Host-client 模式下的远程 XLeRobot 控制。
- 本地大模型 `mimo-v2.5` 的视觉理解和工具调用。
- 本地 Whisper 语音识别。
- Windows SAPI 语音播报。
- 已录制动作序列的录制与播放。
- 键盘遥控入口。

为了避免“一个 Agent 同时看到导航工具、头部工具、动作播放工具后乱调用”，当前新增了 `task_router.py`，先让大模型把用户任务分流到不同路线，再由对应执行器处理。

当前路线包括：

- `recorded_motion`：播放已录制动作。
- `record_motion`：录制/示教新动作。
- `list_motions`：列出已录制动作。
- `navigation_agent`：交给官方 RoboCrew 视觉/导航 Agent。
- `keyboard_control`：进入键盘遥控。
- `chat`：普通聊天或非动作任务。

这个方向已经证明可行，例如“抓盒子”可以直接路由到已录制动作播放，避免模型继续调用底盘移动和环顾工具。

## 2. 当前问题现象

### 2.1 “看看有啥”被误判为动作列表

日志现象：

```text
[识别] 看看有啥
[任务] 看看有啥
[路由] mode=list_motions，理由：用户想查看已录制的动作列表
[结果] 可用动作序列：抓瓶子, 抓瓶子_左臂, 抓盒子
```

实际用户意图更可能是：

- 看当前摄像头画面里有什么。
- 描述机器人前方/当前视野。

但路由器误把“看看有啥”理解成“看看有什么动作”。

### 2.2 “低头看看有啥”只执行低头，没有完成观察描述

日志现象：

```text
[识别] 低头看看有啥
[路由] mode=navigation_agent
Calling look_down with {'angle_degrees': 20} args
[结果] 头部已向下低 20.0 度。下一步只能调用 finish_task 总结结果。
```

实际用户意图是两段式：

1. 低头。
2. 重新观察并描述画面内容。

但当前 `look_down` 返回 `TASK_COMPLETE` 后，程序层认为任务完成，于是没有继续进行“重新获取图像 + 视觉描述”。

### 2.3 “我看看你前面有什么东西”会调用 `look_around`

日志现象：

```text
[识别] 我看看你前面有什么东西
[路由] mode=navigation_agent
Calling look_around with {} args
```

虽然最终描述结果可用，但“前面有什么”通常不需要环顾四周，只需要当前主摄像头画面描述。

这说明：把所有“看/观察”都交给官方导航 Agent，会触发官方 Agent 默认的“环顾四周”倾向。

## 3. 根本原因分析

### 3.1 当前分类路线不够细

现在路由器只有 `list_motions` 和 `navigation_agent`，缺少一个专门的“当前画面观察”路线。

因此用户说：

```text
看看有啥
```

模型只能在已有路线里猜：

- 是看动作列表？
- 是导航观察？

由于 `list_motions` 的描述是“查看已经录制的动作列表”，模型可能把“有啥”误归类到这里。

### 3.2 官方导航 Agent 的 prompt 倾向较强

官方 RoboCrew XLeRobot Agent 原本面向视觉导航任务。它看到“看一下环境”“找东西”“前方有什么”这类任务时，容易调用：

- `look_around`
- `turn_left`
- `turn_right`
- `go_to_precision_mode`
- `move_forward`

这对于真实探索任务是合理的，但对于“只描述当前画面”来说过重。

### 3.3 `TASK_COMPLETE` 对单动作有效，但对复合任务不够

`look_down`、`play_motion`、`record_motion` 等工具返回 `TASK_COMPLETE` 可以防止重复调用工具。

但对于复合任务：

```text
低头看看有啥
```

单个动作完成不等于整个用户任务完成。当前程序没有表达“动作后继续观察”的结构。

## 4. 需要避免的错误优化方式

不要使用以下方式：

```python
if "看看" in task:
    ...
if "抓" in task:
    ...
```

原因：

- 会变成硬编码关键词规则。
- 会导致“只要有某个字就触发某个动作”的误伤。
- 不符合用户希望的大模型语义控制路线。
- 后续动作增多后不可维护。

正确方向应该是：

```text
代码定义清晰路线边界
大模型根据语义选择路线
代码只执行路线对应的工具集合
```

## 5. 建议新增路线

### 5.1 `observe_scene`

用途：

只看当前摄像头画面并描述，不移动底盘，不环顾，不播放动作，不列出动作。

适合：

- 看看有啥。
- 前面有什么。
- 你看到了什么。
- 看一下桌上有什么。
- 当前画面里有什么。

执行逻辑：

1. 获取 `camera_0` 当前图像。
2. 调用视觉模型描述画面。
3. 返回自然语言结果。

注意：

这是语义路线，不是关键词规则。路由器仍然由模型判断是否进入 `observe_scene`。

### 5.2 `head_then_observe`

用途：

先执行一个头部动作，再重新获取图像，并描述新视角。

适合：

- 抬头看看天花板。
- 低头看看桌子上有什么。
- 左边看看有什么。
- 右边看看有什么。

执行逻辑：

1. 路由器输出头部方向，例如 `look_up`、`look_down`、`look_left`、`look_right`。
2. 调用现有头部工具。
3. 重新获取主摄像头图像。
4. 调用视觉模型描述新画面。

重点：

不要把这类任务直接交给完整 `navigation_agent`，否则容易触发环顾、移动、重复调用等行为。

### 5.3 细化 `list_motions`

`list_motions` 只在用户明确询问动作库时使用，例如：

- 有哪些动作？
- 列出录制动作。
- 保存了哪些手势？
- 已录制动作列表。
- 动作库里有什么？

普通“看看有啥”不应进入该路线。

## 6. 建议优化后的路线表

| 路线 | 作用 | 是否移动底盘 | 是否调用官方 Agent |
|---|---|---:|---:|
| `recorded_motion` | 播放已录动作序列 | 否 | 否 |
| `record_motion` | 录制示教动作 | 否 | 否 |
| `list_motions` | 查看动作库 | 否 | 否 |
| `observe_scene` | 描述当前画面 | 否 | 否 |
| `head_then_observe` | 头部动作后观察描述 | 否 | 否 |
| `navigation_agent` | 真实导航/靠近/探索/避障 | 可能 | 是 |
| `keyboard_control` | 键盘遥控 | 人工控制 | 否 |
| `chat` | 普通对话 | 否 | 否 |

## 7. 推荐下一步实现顺序

### 第一步：只改路由类别

在 `task_router.py` 中增加：

- `observe_scene`
- `head_then_observe`

并强化路线说明：

- “看当前画面”优先 `observe_scene`。
- “抬头/低头/左看/右看 + 看看/描述”优先 `head_then_observe`。
- “列出动作/保存动作/手势列表”才进入 `list_motions`。

### 第二步：增加观察执行器

新增函数：

```python
execute_observe_scene(...)
```

职责：

- 捕获主摄像头图像。
- 用视觉模型描述当前画面。
- 不调用机器人动作工具。

### 第三步：增加头部后观察执行器

新增函数：

```python
execute_head_then_observe(...)
```

职责：

- 调用已有头部工具。
- 再捕获图像。
- 再描述新画面。

### 第四步：保留官方 Agent 只处理重任务

`navigation_agent` 只处理确实需要官方 Agent 自主规划的任务，例如：

- 靠近某个物体。
- 往前走一段并观察。
- 环顾四周。
- 找某个物体。
- 避开障碍移动。
- 多步骤移动任务。

## 8. 判断逻辑边界说明

本系统不是纯代码硬分类，也不是让模型随便乱跑。

更准确的结构是：

```text
代码定义“路线类型”和“每条路线允许使用的能力”
大模型根据用户语义选择路线
代码根据路线调用对应的官方/本地工具
```

这比一个 Agent 直接看到所有工具更稳定，因为：

- 播放已录动作时，不会再暴露底盘移动工具。
- 查看画面时，不会再暴露动作库工具。
- 官方导航 Agent 只处理真正需要导航的任务。

## 9. 当前结论

现有路由方案方向正确，但需要从“粗分流”升级为“场景级分流”。

最关键的两个新增路线是：

- `observe_scene`
- `head_then_observe`

这样可以解决：

- “看看有啥”误判为动作列表。
- “低头看看有啥”只低头不描述。
- “前面有什么”不必要地调用 `look_around`。

后续优化应优先做这两条路线，暂时不要继续增加关键词硬规则。
