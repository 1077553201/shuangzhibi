# XLeRobot Host/Client 运行模式说明

日期：2026-05-01  
项目目录：`E:\lerobot`  
机器人控制器：树莓派 5，IP `192.168.10.240`  
主控与训练机器：Windows 高性能电脑

## 1. 核心结论

当前推荐长期采用下面的架构：

```text
树莓派只负责 host / 硬件控制
Windows 负责 client / 遥控 / 数据采集 / 模型训练 / 模型推理
```

也就是：

```text
Windows 是大脑
树莓派是机器人本体控制器
```

这套模式可以支持当前键盘控制，也可以继续扩展到手柄控制、数据采集、训练、模型推理和自动控制。

## 2. Host 是什么

Host 跑在树莓派上。

当前启动命令：

```bash
cd ~/xlerobot-dev/lerobot
source .venv/bin/activate
python -m lerobot.robots.xlerobot.xlerobot_host
```

Host 的职责：

```text
1. 直接连接机器人硬件
2. 读取机械臂、头部、底盘、摄像头状态
3. 接收 Windows client 发来的 action
4. 把 action 转换为底层舵机/轮子控制命令
5. 把 observation 回传给 Windows client
6. 在收不到命令时安全停止底盘
```

树莓派直接接触的硬件包括：

```text
/dev/ttyACM0
/dev/ttyACM1
/dev/video*
```

已知舵机和轮子分布：

```text
/dev/ttyACM0:
  ID 1-6: 左臂关节
  ID 7-8: 头部舵机

/dev/ttyACM1:
  ID 1-6: 右臂关节
  ID 7-9: 底盘轮
```

重要注意：

```text
只有 /dev/ttyACM1 上的 ID 7, 8, 9 是轮子。
其他 ID 都是关节或头部舵机。
```

后续任何自动配置、校准或调试脚本都必须遵守这个区分。

## 3. Client 是什么

Client 跑在 Windows 上。

当前 Windows 端键盘控制脚本：

```text
E:\lerobot\xlerobot_remote_keyboard_client.py
```

推荐运行方式：

```powershell
E:\lerobot\envs\lerobot-gpu\Scripts\python.exe E:\lerobot\xlerobot_remote_keyboard_client.py --ip 192.168.10.240
```

先做连接测试：

```powershell
E:\lerobot\envs\lerobot-gpu\Scripts\python.exe E:\lerobot\xlerobot_remote_keyboard_client.py --ip 192.168.10.240 --smoke
```

Client 的职责：

```text
1. 在 Windows 本机读取键盘、手柄或模型输出
2. 通过局域网把 action 发给树莓派 host
3. 接收树莓派回传的 observation
4. 显示状态和相机画面
5. 保存数据集
6. 加载模型做推理
7. 运行训练和评估脚本
```

## 4. 为什么要采用 Host/Client 模式

之前遇到的问题：

```text
通过 SSH 登录树莓派后，程序监听不到或不能稳定监听 Windows 本机键盘输入。
```

根本原因：

```text
程序实际运行在树莓派上。
它监听的是 SSH 终端输入，不是 Windows 桌面系统的真实键盘事件。
```

Host/Client 模式解决方式：

```text
键盘输入留在 Windows 本机读取。
树莓派只负责硬件控制。
Windows 和树莓派通过局域网通信。
```

这样更适合长期开发：

```text
Windows 有 GPU，适合训练和推理。
Windows 有完整键盘、手柄、显示器，适合交互。
树莓派贴近硬件，适合稳定控制舵机、轮子和摄像头。
```

## 5. 整体数据流

人工遥控时：

```text
Windows 键盘/手柄
  -> Windows client
  -> 局域网
  -> 树莓派 host
  -> 舵机控制板 / 底盘 / 机械臂
```

状态回传时：

```text
机械臂位置 / 底盘状态 / 摄像头画面
  -> 树莓派 host
  -> 局域网
  -> Windows client
```

模型控制时：

```text
树莓派 host 返回 observation
  -> Windows client
  -> Windows GPU 模型推理
  -> 生成 action
  -> 发送给树莓派 host
  -> 机器人执行动作
```

数据采集时：

```text
Windows client 遥控机器人
  -> 同时接收 observation 和 action
  -> 保存为 LeRobot dataset
  -> 后续用于训练
```

## 6. 哪些事情交给树莓派

树莓派应该继续负责：

```text
1. 运行 xlerobot_host
2. 连接 Feetech 舵机控制板
3. 连接底盘轮
4. 连接摄像头
5. 读取硬件状态
6. 下发底层舵机命令
7. 硬件校准
8. 查找 /dev/ttyACM* 和 /dev/video*
9. 舵机 ID 设置
10. 舵机运行模式配置
11. 硬件级安全停止
```

原因：

```text
这些操作依赖物理连接的硬件。
硬件接在树莓派上，所以底层硬件操作应该留在树莓派端。
```

## 7. 哪些事情交给 Windows

Windows 应该负责：

```text
1. 键盘控制
2. 手柄控制
3. 任务脚本
4. 可视化界面
5. 相机画面显示
6. 数据集保存
7. 数据清洗和管理
8. 模型训练
9. 模型评估
10. 模型推理
11. 实验记录
12. 后续网页控制或桌面控制界面
```

原因：

```text
Windows 有 RTX 4060 Laptop GPU。
Windows 计算性能更强。
Windows 更适合运行训练、Jupyter、可视化和交互式控制。
```

当前 Windows CUDA 环境：

```text
E:\lerobot\envs\lerobot-gpu
```

已验证：

```text
torch 2.10.0+cu130
cuda_available True
GPU: NVIDIA GeForce RTX 4060 Laptop GPU
```

## 8. 这套模式能否运行所有相关代码

准确说：

```text
Host/Client 模式不是让一个 client 脚本运行所有代码。
它是后续所有远程控制、数据采集、模型推理的通信基础。
```

可以基于这套模式继续实现：

```text
1. 键盘遥控
2. 手柄遥控
3. 机器人状态读取
4. 摄像头画面回传
5. 数据集录制
6. 训练数据整理
7. Windows GPU 训练
8. 模型推理控制机器人
9. 自动任务脚本
```

但仍然不建议把下面这些放到 Windows 直接做：

```text
1. 直接访问 /dev/ttyACM*
2. 直接访问树莓派上的 /dev/video*
3. 舵机 ID 配置
4. 底层串口调试
5. 机器人本体校准
```

这些应继续在树莓派上做。

## 9. 当前可立即运行的流程

第一步，在树莓派启动 host：

```bash

```

如果提示：

Press ENTER to restore calibration from file, or type 'c' and press ENTER to run manual calibration:

第二步，在 Windows 连接测试：

```powershell
E:\lerobot\envs\lerobot-gpu\Scripts\python.exe E:\lerobot\xlerobot_remote_keyboard_client.py --ip 192.168.10.240 --smoke
```

第三步，在 Windows 运行键盘控制：

```powershell
E:\lerobot\envs\lerobot-gpu\Scripts\python.exe E:\lerobot\xlerobot_remote_keyboard_client.py --ip 192.168.10.240
```

退出：

```text
ESC
```

退出时 Windows client 会发送零底盘速度，避免底盘持续运动。

## 10. Host 输出的含义

如果树莓派 host 输出：

```text
WARNING:root:No command available
```

含义：

```text
host 正在运行，但是还没有收到 Windows client 的控制命令。
```

如果输出：

```text
Command not received for more than 500 milliseconds. Stopping the base.
```

含义：

```text
host 超过 500ms 没有收到控制命令，因此为了安全主动停止底盘。
```

这通常不是错误，而是安全机制。

## 12. 推荐开发顺序

建议不要直接跳到训练，先把控制和数据闭环打稳。

推荐顺序：

```text
1. 树莓派 host 稳定启动
2. Windows smoke test 能收到 observation
3. Windows 键盘控制能安全控制底盘小速度
4. Windows 键盘控制能安全控制左右臂小幅动作
5. ESC 退出能稳定停止底盘
6. 接入并显示摄像头 observation
7. 录制小规模人工遥控数据
8. 检查数据集格式和质量
9. Windows GPU 训练小模型
10. 模型离线评估
11. 模型在线低速接管控制
12. 逐步扩大任务和动作范围
```

## 13. 对刚才问题的明确回答

问题：

```text
现在键盘控制可以运行，树莓派只运行 host，然后把后续所有控制交给 Windows 可以吗？
我在 Windows 程序运行模型训练等？
```

回答：

```text
可以。
这正是当前推荐架构。
```

更准确地说：

```text
树莓派负责底层硬件控制和安全执行。
Windows 负责上层控制、遥控输入、数据采集、训练、推理和可视化。
```

这套结构可以长期使用。

但边界是：

```text
硬件直接相关的底层操作仍然在树莓派端执行。
上层算法、模型、交互、训练都放在 Windows 端执行。
```

## 14. 最重要的安全原则

后续所有 Windows 控制程序都应该遵守：

```text
1. 启动时先读取当前 observation，不要把关节目标突然归零。
2. 底盘速度默认是 0。
3. 没有持续控制输入时，底盘速度应回到 0。
4. 退出程序时必须发送停止命令。
5. 第一次测试任何新控制逻辑时都使用低速度、小幅度。
6. 左右臂和底盘分开测试。
7. 模型接管前必须先离线验证 action 范围。
8. 模型在线测试时要保留人工急停方式。
```

当前最优先的下一步：

```text
让树莓派 host 和 Windows keyboard client 稳定跑通。
确认 observation、action、安全停止都正常。
```
