
第一次 host 运行后出现过错误：

```text
ConnectionError: Failed to write 'Lock' on id_=7 with '1' after 1 tries.
[TxRxResult] There is no status packet!
```

排查后发现，底盘轮所在的 `/dev/ttyACM1` 上 ID 7, 8, 9 能响应读取，但写入 `Lock` 后没有返回状态包。后来调整过舵机通讯返回状态级别 `Response_Status_Level`，使写入操作能收到返回包。

需要澄清：

```text
Response_Status_Level 不是舵机运行模式。
它只影响舵机是否对读写命令返回状态包。
```

因此它不是“把舵机改成轮子模式”。真正表示运行模式的是 `Operating_Mode`。

当时看到的模式判断：

```text
普通关节/头部:
  Operating_Mode = 0

底盘轮:
  Operating_Mode = 1
```

后续再次运行 host 时出现：

```text
WARNING:root:No command available
WARNING:root:Command not received for more than 500 milliseconds. Stopping the base.
```

这不是新的硬件错误。含义是树莓派 host 已经在等待 Windows 端发送控制命令，但当时 Windows 客户端还没有连接，所以 host 为了安全停止底盘。


这个脚本的用途：

```text
在 Windows 上读取键盘输入，通过 ZeroMQ 连接树莓派 host，并发送 XLeRobot 控制命令。
```

创建这个脚本的原因：

1. 用户之前通过 SSH 连树莓派时，树莓派上的程序无法正常监听 Windows 本机键盘输入。
2. 正确方式应该是树莓派跑 host，Windows 跑 client。
3. 键盘事件应在 Windows 本地捕获，再通过网络发给树莓派。
4. 这样后续也方便替换为手柄、网页控制、策略模型控制或录制数据。

脚本特点：

```text
默认连接 IP: 192.168.10.240
默认命令端口: 5555
默认观测端口: 5556
使用 pynput 捕获键盘
使用 pyzmq 通讯
使用 numpy/cv2 处理观测相关依赖
启动时不会把关节目标强制置零，而是先读取当前 observation，避免机械臂突然动作
退出时会发送零底盘速度，避免底盘继续运动
```

脚本参数验证已通过：

## 6. Windows 环境选择过程

最开始评估过 miniconda 和 uv。

最终选择 uv 的原因：

1. conda 在当前 Windows 机器上遇到用户目录权限/缓存/TOS 插件相关问题。
2. conda 尝试创建环境时会写入 `C:\Users\10775\AppData\Local\conda...`，实际运行中受阻。
3. uv 创建虚拟环境更轻量，速度更快，目录也可以明确放在 `E:\lerobot` 下。
4. 对这个项目来说，uv + pip wheel 已经可以满足 LeRobot/XLeRobot 的主要依赖。

uv 安装位置：

```text
E:\lerobot\uv-site\bin\uv.exe
```

成功创建的 Windows GPU 环境：

```text
E:\lerobot\envs\lerobot-gpu
```

Python 版本：

```text
Python 3.12.13
```

选择 Python 3.12 的原因：

1. LeRobot 和深度学习生态对 Python 3.12 的 wheel 支持比 Python 3.13 更稳定。
2. 当前系统 Python 是 Python 3.13.11，部分包在 3.13 上需要源码编译，失败概率更高。
3. PyTorch CUDA wheel 对 Python 3.12 支持成熟。

## 11. 当前风险与注意事项

### 11.1 轮子模式不要误改全部舵机

必须记住：

```text
/dev/ttyACM1 上的 ID 7, 8, 9 是轮子。
其他 ID 是关节。
```

不能把所有舵机都设置成轮子模式。

后续如果写任何自动配置脚本，必须按总线和 ID 精确区分。

### 11.2 不建议修改官方源码来绕硬件问题

用户明确指出“尽量不要改官方文档”。当前策略是：

1. 先按官方/上游 XLeRobot 结构跑通。
2. 对硬件通讯问题优先查配置、舵机参数、总线、供电。
3. 只有确认是兼容性问题且无法通过配置解决时，才做最小补丁。
4. 所有补丁都要记录原因和回滚方式。

目前没有把跳过 `Lock` 的补丁同步到树莓派，官方 XLeRobot 代码基本保持原样。

### 11.3 Windows `lerobot[all]` 的 placo 问题

当前环境没有 `placo`。

影响：

```text
可能影响 IK/运动学相关功能。
不影响当前 XLeRobot host/client、舵机控制、数据采集、训练主线。
```

后续如果需要补装：

1. 先安装 Visual Studio Build Tools。
2. 再单独尝试安装 `placo` 或 `lerobot[kinematics]`。
3. 不建议现在为了这个阻塞主线。

### 11.4 uv Python trampoline 权限现象

在普通沙箱命令里直接运行：

```powershell
E:\lerobot\envs\lerobot-gpu\Scripts\python.exe
```

曾出现：

```text
error: uv trampoline failed to spawn Python child process
permission denied (os error 5)
```

提升权限后运行正常。

判断：

```text
这是当前 Codex/Windows 沙箱对 uv Python 启动器跨目录启动真实解释器的限制，不是环境损坏。
```

用户在本机 PowerShell 正常使用时大概率不会遇到这个限制。如果遇到，可以尝试：

1. 用普通 PowerShell 直接运行。
2. 以管理员方式打开 PowerShell。
3. 重新创建 venv 时尝试使用 copy 模式，减少 uv trampoline 依赖。
